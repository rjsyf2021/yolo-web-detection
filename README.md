# YOLO Web Detection

[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](LICENSE)

在浏览器中检测图片、视频和摄像头画面。服务端使用 YOLO26 检测模型与 TensorRT，实时摄像头支持 JPEG/WebSocket 和 WebRTC/MediaMTX，可选客户端或服务器画框。

这是持续迭代的个人项目，代码结合 AI 辅助开发。当前面向 Linux NVIDIA GPU 服务器与受信任网络，未提供账号鉴权和用户隔离，也未完成每次提交的真实 GPU、浏览器端到端验证。

**模型需自备。** 仓库不包含 `.pt`、`.onnx` 或 `.engine`，导出脚本不自动下载权重。应用仅加载 `yolo26[nsmxl]_640x640.engine` 检测引擎，不支持任意 YOLO 版本、分割、姿态或分类模型。

## 快速启动

下面的命令在仓库根目录执行。先用一张图片确认模型可用，再测试视频和摄像头。

### 1. 准备运行环境

需要已配置好的 Linux NVIDIA GPU 环境，驱动、PyTorch、torchvision、Ultralytics 和 TensorRT 应与模型及引擎兼容。应用不自动安装或升级这些 GPU 组件。可在已有虚拟环境中检查 CUDA，再补充应用依赖：

```bash
source /path/to/yolo_env/bin/activate
nvidia-smi
python -c "import torch; print('PyTorch:', torch.__version__, 'CUDA:', torch.version.cuda, 'GPU可用:', torch.cuda.is_available())"
python -m pip install -r requirements.txt
```

将 `/path/to/yolo_env` 换成实际环境路径；已有完整依赖时不必重复安装。`requirements.txt` 不是完整版本锁文件，也不包含导出所需的全部 GPU 依赖。CUDA 可用检查通过，不代表引擎一定兼容。

视频使用 PyAV 编解码；音轨封装还会调用 FFmpeg。GPU JPEG 解码为可选能力，缺少 nvImageCodec 时使用 OpenCV。WebRTC 不使用 aiortc。

### 2. 准备模型：二选一

**已有兼容引擎：** 把至少一个引擎放在 `app_ws-multi.py` 同目录，例如：

```text
yolo-web-detection/
├── app_ws-multi.py
└── yolo26s_640x640.engine
```

型号可为 n、s、m、l、x，文件名必须对应实际模型。引擎实际输入必须为 640×640，不能通过重命名改变输入尺寸；旧的矩形引擎会被忽略。只有引擎时不需要 `.pt` 权重或执行导出。

**只有本地权重：** 将对应的 `yolo26s.pt` 等权重放在脚本目录，使用导出工具：

```bash
# 示例：只导出本地的 yolo26s.pt
python export_all_engines.py --models s --list
python export_all_engines.py --check-env
python export_all_engines.py --models s
```

当前导出脚本要求 CUDA 13 版 PyTorch 与 ONNX Runtime、TensorRT 11 或更高版本及 ModelOpt；这是导出脚本的要求，应用运行已有引擎时仍以引擎兼容性为准。默认导出 640×640、batch=1，已有有效目标默认跳过。完整环境说明、覆盖行为和其他型号命令见 [模型导出说明](docs/EXPORT.md)。

### 3. 启动应用

```bash
# 引擎位于脚本目录
python app_ws-multi.py
```

也可把引擎集中放在 `models/`：

```bash
ENGINE_DIR=./models python app_ws-multi.py
```

应用默认监听 `0.0.0.0:7860`。等待终端出现启动预热完成信息：本机浏览器访问 `http://localhost:7860`；另一台设备访问服务器地址和端口。`0.0.0.0` 是监听地址，不是浏览器访问地址。

首次进入 **图片 / 视频**，选择一张图片和已有模型，点击 **批量上传并检测**，确认能预览和下载结果。只用图片、视频或 JPEG 摄像头时无需启动 MediaMTX。

**远程摄像头需要浏览器信任的 HTTPS 页面。** 能通过服务器 HTTP 地址打开页面，不代表能使用手机摄像头；`localhost` 仅指浏览器所在设备。HTTPS 代理应同时支持 WebSocket。

## 图片与视频

### 基本操作

1. 打开 **图片 / 视频**，选择一个或多个文件，可混选图片和视频。
2. 选择引擎、策略、置信度及同时处理数量。首次排查可用单项处理；页面默认并发为 3。
3. 点击 **批量上传并检测**，每项显示上传、处理和完成状态。
4. 点击该项 **预览** 查看原文件和结果，完成后点击 **下载检测结果**。结果有保留期限，请及时下载。

图片输出为标注后的 JPEG。视频输出为 MP4，优先硬件编码，初始化失败时尝试软件编码；源音轨的保留情况应以结果及处理日志为准。输入格式是否可用取决于当前 OpenCV、PyAV 和 FFmpeg 的解码能力，浏览器允许选择文件不等于服务器一定支持其编码。

### 参数与任务控制

| 页面选项 | 实际行为 |
| --- | --- |
| 引擎 | 手动指定已有型号，或自动选择模型规模；网络输入都为 640×640 |
| 策略 | 自动选择时生效：速度优先 n、均衡优先 s、细节优先 x；缺少时按可用型号回退。默认细节，大模型不保证每种素材都更准确 |
| 置信度 | 默认 0.40，范围 0–1；提高会过滤更多低置信度框，不保证消除所有误检 |
| 同时处理 | 前端 1–4 项，默认 3；服务端还受 `MEDIA_WORKERS` 和 GPU 实例数限制 |
| 取消此任务 | 取消单项，其他任务继续；正在执行的推理需等当前调用返回 |
| 重新开始 | 完成、失败或取消后可用；先调整页面参数，再点击，使用点击时的模型、策略和置信度 |
| 删除文件与记录 | 取消该项，并清理它历次重新开始留下的服务器文件；正在使用的文件延后清理 |
| 停止所有进行中任务 | 暂停后续队列并请求取消进行中的任务 |
| 清空全部记录 | 对当前队列全部项目执行取消、删除和移除记录 |

处理期间可继续选文件追加到队列。单项重试不会启动其他尚未开始的文件；重试入队后再次修改页面参数，不会改变这次重试的设置。保留期内复用服务器源文件，过期后页面仍持有本地文件时会尝试重新上传；刷新页面后可能需要重新选文件。

图片在原始分辨率画框。视频会按旋转信息和像素宽高比校正显示画幅，并按源时间戳播放；YUV420 编码遇到奇数宽高时最多补一像素。模型内部的 640×640 灰边补齐不会把结果视频变成正方形。

## 实时摄像头

### 先使用 JPEG

1. 在可信 HTTPS 页面或本机 localhost 打开 **实时摄像头**。
2. 选择摄像头，传输选 **JPEG**，选定已有模型、画幅和目标帧率。
3. 点击 **开始摄像头** 并允许浏览器权限。
4. 查看页面中的实际采集尺寸、源帧率、检测 FPS 和处理耗时，结束时点击 **停止**。

页面初始配置为客户端画框、4:3、1080p、目标 60 FPS、置信度 0.40，实时模型优先选择可用的 s。设备、网络或服务端跟不上时，可降低采集分辨率和帧率，再比较处理结果。

### 选择画框与队列方式

| 选项 | 适用需求与代价 |
| --- | --- |
| 客户端画框 | 浏览器显示本地摄像头并叠加返回的框；画面较新，框可能来自稍早帧 |
| 服务器画框（同帧） | 显示服务器标注的画面，框与帧对应；多出画框、编码、回传和播放开销 |
| 顺序处理 / FIFO | 最多 4 张应用待处理帧，按顺序处理；上游仍可能积压，不能理解为总延迟最多 4 帧 |
| 低延迟 | 只保留最新一张待处理帧，替换旧待处理帧；不取消正在推理的帧，也不消除网络和播放缓冲 |

JPEG 和 WebRTC 各有独立队列选择。FIFO 不保证浏览器展示每个采集帧；需要保留完整视频内容时使用文件上传。

### 画幅与参数

| 比例 | 720p | 1080p |
| --- | --- | --- |
| 16:9 | 1280×720 | 1920×1080 |
| 4:3 | 960×720 | 1440×1080 |

竖屏交换宽高，自动方向根据实际视频画面判断。这里是应用请求和显示的画幅，硬件协商后的源尺寸可能不同，以页面统计为准。等比例容纳画面时可能补边；推理仍为 640×640，检测框还原到显示画幅。

| 参数 | 作用范围与说明 |
| --- | --- |
| 摄像头目标帧率 | 两条通道共用；可选 10、15、20、24、25、30、40、45、50、60 FPS，默认 60；无法把 30 FPS 源变成真实 60 FPS |
| JPEG 质量 | 仅 JPEG，65%–98%，默认 90%；影响浏览器编码开销、上传体积和画质 |
| JPEG 编码 | 默认兼容编码；后台编码为试用选项，异常时可切回兼容模式 |
| 发送缓冲 | 仅 JPEG，默认兼容 512KB；低积压模式收紧浏览器发送缓冲门槛，不等于服务端低延迟队列 |
| WebRTC 码率上限 | 0.5–50 Mbps 档位，默认 8 Mbps；上行为浏览器上限，服务器画框回传另用同档目标，并非共享带宽配额 |
| WebRTC 解码 | 自动：优先 NVDEC，失败尝试 CPU；仅 NVDEC：失败不回退；仅 CPU：使用软件解码 |

WebRTC 会向浏览器请求分辨率优先，实际支持与降帧行为以页面读回状态为准。切换传输方式后需要重新开始；更换模型、比例、分辨率或画框位置会重启正在运行的会话。WebRTC 的码率、解码、队列和帧率变化也会触发重新协商。

JPEG 对慢客户端使用独立结果发送队列，最多排队 4 个结果；单次发送超过 10 秒会关闭连接。断开后需要重新开始，不会无限堆积待发送结果。

## WebRTC 部署

完成 JPEG 路径验证后，再配置 WebRTC。它需要额外运行 MediaMTX：浏览器发布视频，应用通过 RTSP 接收；服务器画框时还要把标注视频经 MediaMTX 回传。

### 配置 MediaMTX

```bash
# 首次配置时执行；已有配置请保留，勿直接覆盖
cp mediamtx.example.yml mediamtx.yml
```

编辑 `mediamtx.yml`，将 `webrtcAdditionalHosts` 的占位符换成客户端可达的服务器地址，例如局域网地址。示例配置的端口用途：

| 端口 | 默认监听 | 用途 |
| --- | --- | --- |
| TCP 7860 | 所有网卡 | 应用网页、API、WebSocket；HTTPS 代理转发到这里 |
| TCP 8554 | 127.0.0.1 | 内部 RTSP 收发 |
| TCP 8889 | 127.0.0.1 | 内部 WebRTC 信令，由应用代理 |
| UDP 8189 | 所有网卡 | 浏览器与 MediaMTX 的媒体传输，需要网络可达 |

### 选择一种启动方式

**分别启动：** 第一个终端运行 MediaMTX，第二个终端启动应用。

```bash
# 终端一：缺少缓存时下载脚本固定版本的 MediaMTX
./start_mediamtx.sh
```

```bash
# 终端二：激活已配置好的环境后执行
python app_ws-multi.py
```

`start_mediamtx.sh` 当前下载并缓存 MediaMTX v1.21.1，支持 Linux amd64/arm64，首次需要 `curl`、`tar` 和网络，不安装 Python 包。已有手动安装的 MediaMTX 也可用自己的启动命令，但配置须与版本兼容。

**统一启动：** 不要同时运行上面的独立服务，改用：

```bash
YOLO_VENV=/path/to/yolo_env ./start.sh
```

`start.sh` 需要 Bash 5.1+、`ss`、`setsid` 和已编辑好的 `mediamtx.yml`，默认虚拟环境为 `~/yolo_env`。它等待 MediaMTX 监听默认 8554 端口，再启动应用；已有服务占用该端口时会退出。按 Ctrl+C 或任一服务退出会停止本次启动的另一服务，约 5 秒后仍未退出的子进程会被强制结束，残留任务文件留待下次启动清理。

应用预热完成后，在页面选择 **WebRTC** 并开始摄像头。模型预热只在启动/重新加载时执行，但 ICE 协商、编解码器准备和首帧接收仍需要时间。

### 远程访问

HTTP 反向代理不会自动代理 WebRTC 的 UDP 媒体。HTTPS、DDNS 和 `webrtcAdditionalHosts` 也不能代替防火墙、路由或 NAT 配置。当前示例关闭自动网卡发现，不能只删除地址占位符而不提供可用的发现配置。

应用没有鉴权和用户隔离。若通过公网访问，需要在部署层保护网页、上传/下载 API、WebSocket 和 WebRTC 信令，并配置访问与连接限制；本仓库未提供开箱即用的生产公网部署方案。

## 服务端配置

应用读取进程环境变量，不会自动读取 `.env`。相对目录以进程工作目录为准；默认模型目录则固定为脚本所在目录。

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `ENGINE_DIR` | 脚本目录 | 已有引擎目录；不改变导出脚本输出位置 |
| `PORT` | 7860 | 应用 HTTP 端口 |
| `MEDIA_WORKERS` | 4，限制 1–4 | 服务端文件工作线程数，区别于前端同时处理数量 |
| `MEDIA_TEMP_DIR` | 系统临时目录下按用户和脚本路径区分的专属目录 | 源文件、结果与锁文件存放位置 |
| `ENGINE_CACHE_SIZE` | 未设置时尝试保留全部模型 | 限制常驻模型种类数，最低 1；显存不足仍可逐出模型 |
| `ENGINE_REPLICAS` | 2，限制 1–4 | 每种常驻模型启动时尝试创建的实例数 |
| `GPU_RESERVE_MB` | 2048，最低 512 | 加载实例时预留显存预算，不是显存占用硬上限 |
| `MEDIAMTX_HTTP` | `http://127.0.0.1:8889` | MediaMTX 信令地址 |
| `MEDIAMTX_RTSP` | `rtsp://127.0.0.1:8554` | MediaMTX RTSP 地址 |
| `YOLO_VENV` | `~/yolo_env` | 仅供 `start.sh` 选择 Python 环境 |
| `MEDIAMTX_START_TIMEOUT` | 60 秒 | 仅供 `start.sh` 等待 MediaMTX 默认 RTSP 端口 |

例如限制为一种常驻模型、一个实例和一个文件工作线程：

```bash
ENGINE_DIR=./models ENGINE_CACHE_SIZE=1 ENGINE_REPLICAS=1 MEDIA_WORKERS=1 python app_ws-multi.py
```

这不能解决单个模型本身超出可用显存的问题，也不保证更快。启动时按真实空闲显存和估算预算创建副本；运行中显存紧张会释放额外空闲副本，忙碌副本用完再释放，降级持续到进程重启。各实例可并行，但同一实例串行使用。

模型被缓存逐出后再次选中仍需初始化。多文件会竞争 GPU、CPU 和编解码资源，应比较总完成时间，不能只看单个任务 FPS。服务端最多接受 32 个未结束文件任务；图片/视频上传没有新增单文件容量限制，磁盘及内存仍需自行管理。实时 JPEG 消息有独立大小限制。

## 文件保留与清理

| 情况 | 行为 |
| --- | --- |
| 完成、失败或取消 | 从结束时刻保留源文件和结果 15 分钟；查看和下载不续期 |
| 到期 | 拒绝新下载和复用请求；约每 10 秒检查清理，正在下载或收尾的任务等待结束 |
| 重新开始 | 创建新任务和新的保留期限；单项删除可一并清理历次重试文件 |
| 正常退出 | 等待处理线程结束后清理任务文件；重启不恢复旧任务或结果 |
| 强制终止、断电 | 下次使用同一目录启动并取得锁后清理；未重启期间残留仍可能存在 |
| 清理失败 | 等待至少 10、20、40、80 秒依次重试；累计失败 5 次停止自动重试，保留错误记录 |

专属目录必须位于支持 Linux 文件锁的本地文件系统，现有目录须归运行用户所有且权限为 700；不存在时由应用创建。可使用 `MEDIA_TEMP_DIR` 指定独立目录，请勿把个人资料目录用作临时目录。

同一目录只能由一个应用实例持有。旧实例未退出时新实例拒绝启动；不要在运行中删除 `.lock`，也不要使用多个 Uvicorn worker。目录中的 `job-<32位标识>` 由应用管理，清理跳过符号链接和未知名称，锁文件保留。

旧版本散落在 `/tmp` 下的 `yolo-media-*` 没有可靠归属标记，不会自动清理；移动项目或更换临时目录后，旧目录也需在确认旧实例停止后处理。不要用宽泛的通配删除命令清理整个 `/tmp`。清理放弃时终端和任务状态会保留 `cleanup_error`、`cleanup_failures`、`cleanup_abandoned`，需人工排查权限/磁盘问题，后续退出或启动会再次尝试清理。

临时文件未做应用层加密，当前也没有用户隔离。15 分钟是保留策略，不是任何异常情况下都能保证的删除时限。

## 性能统计与测速

```bash
python benchmark_fps.py --list
python benchmark_fps.py --image /path/to/sample.jpg --variants s m --render server
python benchmark_fps.py --image /path/to/sample.jpg --source-sizes original --render none
```

默认源画幅为 1280×720、1920×1080、960×720、1440×1080，网络输入均为 640×640。引擎在其他目录时添加 `--dir ./models`；报告默认写到脚本目录的 `fps-benchmark.json`，可用 `--json` 指定路径。已有兼容引擎即可测速，无需 `.pt`。

| 指标 | 应如何理解 |
| --- | --- |
| benchmark FPS | 预测、坐标后处理和可选画框的速度；不含图片读取、源画幅生成、视频编解码和网络 |
| 视频处理 FPS | 离线处理吞吐；30 FPS 视频以 60 帧/秒处理，成片仍按源时间戳播放 |
| 实时检测 FPS | 当前通道得到检测结果的速率，不等于摄像头采集或屏幕刷新率 |
| `infer_ms` | 应用中的预处理、推理、后处理和结果搬运耗时，不是纯 TensorRT 内核运行时间 |
| RTT / 服务器耗时 | 各有测量范围，不能单独当作摄像头到屏幕的端到端延迟 |
| benchmark 显存峰值 | 仅覆盖 PyTorch 分配器，不含全部 TensorRT/CUDA 分配 |

`--render server` 包含原图画框，`none` 不画框。未提供默认本地图片时使用合成画面，不联网下载；其检测数量和画框开销不代表真实素材。流水线阶段可以重叠，不应把各阶段平均耗时简单相加后换算并行吞吐。

项目此前记录的 **Tesla T10 16 GB** 测速表、素材及测试条件见 [基准测速与历史结果](docs/BENCHMARK.md)。对比时固定模型、素材、置信度、画框方式和并发数，历史数据不代表其他硬件或每次提交的性能。

## 常见问题

| 现象 | 先检查什么 |
| --- | --- |
| 未找到引擎 | `ENGINE_DIR`、文件名、目录权限；至少一个实际为 640×640 的检测引擎 |
| 模型不在列表 | 是否矩形旧引擎、命名错误或启动预热失败；新增引擎后重启服务 |
| 引擎加载失败 | GPU/TensorRT 兼容性、输入绑定形状、显存；必要时在目标环境重新导出 |
| 显存不足或并发越高越慢 | 减少前端并发、`MEDIA_WORKERS`、`ENGINE_REPLICAS`；查看其他 GPU 进程，缓存限制不能缩小单模型 |
| 页面能打开但摄像头不能用 | HTTPS 是否被浏览器信任、权限、设备占用；手机上的 localhost 不是服务器 |
| 选择 60 FPS 实际只有 30 | 看实际源、轨道、编码和检测统计；硬件能力上限不保证每种分辨率组合都支持 |
| WebRTC 有页面但无视频 | MediaMTX 日志、地址占位符、UDP 8189、防火墙/NAT；先确认 JPEG 可用 |
| NVDEC 报错或回退 CPU | 看首帧前后的异常与重试日志；可切仅 CPU 对照，`invalid data` 不足以证明 GPU 不支持 |
| 服务器画框更慢 | 对照客户端画框，检查编码/回传耗时和播放缓冲 |
| 修改置信度后旧结果没变 | 文件任务需点击该项重新开始；只改页面参数不会修改已生成的结果 |
| 结果过期或服务重启后无法下载 | 原任务不会恢复，需要重新上传处理 |
| 提示临时目录被占用 | 确认旧服务是否仍运行，不要删除锁文件绕过保护 |
| 提示临时目录权限错误 | 确认是当前用户的专属目录，权限 700；避免符号链接或共享资料目录 |
| 删除失败、磁盘仍有文件 | 检查是否正在下载/处理及清理错误日志；累计失败后需人工处理 |
| 上传提示 HTTP 413 | 检查反向代理等部署层的大小限制；应用未新增图片/视频容量限制 |
| 修改代码后页面没变化 | 重启对应服务并刷新页面，确认访问的地址和进程正确 |

## 开发与反馈

### 回归测试

静态检查使用仓库根目录的 `.pylintrc`，可在独立的 CPU 虚拟环境运行：

```bash
python -m pip install -r requirements-dev.txt
python -m pylint $(git ls-files '*.py')
```

CI 以错误和警告检查为准，命名、行长、文档字符串和复杂度等风格建议不作为阻断条件。仅对部署环境提供的 GPU/导出依赖及 OpenCV、PyAV 动态接口设置模块级例外；其他导入、未定义变量、项目代码成员及语法错误仍会使检查失败。会话异常隔离、回调参数和 lifespan 管理的全局池另有明确例外。CI 不应使用 `--exit-zero` 或 `continue-on-error` 隐藏检查失败。

在仓库根目录运行：

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
```

测试源码随仓库提交，不需要模型权重或 CUDA。基准和导出测试使用替身验证调度、错误报告与文件替换；实时健壮性测试验证慢客户端、结果顺序、超时与断连回收、清理退避和帧率校验；视频测试使用替代推理和真实编解码，需要 `numpy`、`opencv-python`、`av`，以及 PATH 中支持 `libx264` 和 AAC 的 `ffmpeg`。缺少视频测试依赖时会显示 `skipped`，不代表该部分已验证。

生成的视频和模拟引擎放在系统临时目录，测试结束自动清理；无需把 `tests/` 加入 `.gitignore`。这些测试不能替代目标机器上的真实 GPU 导出、推理性能和浏览器 WebRTC 验证。
