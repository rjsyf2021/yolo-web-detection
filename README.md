# YOLO Web Detection
[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](LICENSE)

这是一个持续迭代的个人项目。代码由开发者结合 AI 辅助完成，性能取决于输入、模型、浏览器和服务器配置。

**模型需由使用者自行准备。** 本仓库不提供模型权重（`.pt`）、ONNX 模型或 TensorRT 引擎（`.engine`），也不提供模型自动下载功能。使用者可准备兼容的引擎直接运行，或使用自备权重通过导出脚本生成引擎。

## 功能

- 图片与完整视频上传，服务器推理、画框，结果预览和下载。
- 批量队列、1–4 项同时处理、停止任务及清除队列。
- JPEG / WebSocket 与 WebRTC / MediaMTX 两条实时传输路径。
- 客户端或服务器画框；横竖屏适配；采集可选 4:3、16:9 和 720p、1080p，模型推理固定 640×640。
- WebRTC 10–60 FPS 目标帧率、0.5–50 Mbps 码率档位，分辨率优先策略。
- WebRTC FIFO 4 帧或单张待处理帧的低延迟模式。
- 启动模型预热、硬件解码与编码回退、各阶段耗时统计。

## 架构

~~~text
图片/视频文件 → FastAPI → 解码 → TensorRT → CPU画框 → 编码 → 下载
浏览器JPEG   → WebSocket → 解码 → TensorRT → 检测框或标注JPEG
浏览器WebRTC → MediaMTX → RTSP解码 → TensorRT → 检测框
                                             └→ 画框/编码 → MediaMTX → 浏览器
~~~

单个视频采用解码、推理、画框、编码流水线；不同视频各有画框与编码线程。启动时在显存预算允许的情况下为每个常驻模型准备多个独立推理实例，同一实例串行使用，不同实例可并发。增加文件并发不保证单视频 FPS 或总吞吐提高。

## 部署

### 1. GPU 环境

使用已有的 Linux NVIDIA GPU 环境，先安装匹配驱动、CUDA、PyTorch、torchvision、Ultralytics 和 TensorRT。项目不自动升级这些组件，也不包含模型或 GPU 运行库。

在原来的虚拟环境中补充应用依赖：

~~~bash
source /path/to/yolo_env/bin/activate
python -m pip install -r requirements.txt
~~~

已有能运行的环境无需重复安装。requirements.txt 是依赖清单，不是完整、已验证的版本锁文件。已有服务器使用 PyAV 19.0.1；没有引入 aiortc。

### 2. 准备模型并启动

将自行准备的 YOLO26 检测权重放在脚本目录，文件名为 `yolo26n.pt`、`yolo26s.pt`、`yolo26m.pt`、`yolo26l.pt` 或 `yolo26x.pt`。export_all_engines.py 会自动发现已有权重，为每个型号导出一个 640×640 引擎，也可用 `--models m l x` 指定型号。输出在脚本目录，具体命令见 [模型导出说明](docs/EXPORT.md)。直接使用这些引擎时运行 `python app_ws-multi.py`。已有兼容引擎的使用者无需准备 `.pt` 权重或执行导出。

如果希望单独存放模型，可将自己导出的 TensorRT 引擎放在 models/，使用下方的 ENGINE_DIR 启动命令。文件名必须符合当前扫描规则，例如 yolo26s_640x640.engine、yolo26m_640x640.engine。当前应用仅加载 yolo26[nsmxl]_640x640.engine，不是任意 YOLO 版本的通用加载器。

模型输入为 640×640，必须与引擎实际形状一致，不能靠改名改变模型输入。Ultralytics LetterBox 等比例缩放并补灰边（114），后处理把检测框映射回原始画面；摄像头和文件输出不会变成 640×640。引擎需要与部署环境兼容，旧的矩形引擎会被忽略。

~~~bash
ENGINE_DIR=./models python app_ws-multi.py
~~~

默认监听 0.0.0.0:7860。启动预热结束后浏览器访问服务器页面。远程手机摄像头需要浏览器信任的 HTTPS；localhost 可用于本机访问。HTTPS 反向代理需要支持 WebSocket。

### 3. WebRTC（可选）

JPEG 路径无需 MediaMTX。WebRTC 需要单独安装 [MediaMTX](https://mediamtx.org/docs/kickoff/install)，并使用与其版本兼容的配置。

~~~bash
cp mediamtx.example.yml mediamtx.yml
# 编辑 webrtcAdditionalHosts：把占位符换成客户端可达的服务器地址
./mediamtx mediamtx.yml
~~~

示例将 RTSP 8554 和信令 HTTP 8889 绑定回环地址，UDP 8189 用于 WebRTC 媒体传输；网页请求由应用代理信令。跨网访问还涉及防火墙、NAT 与 ICE，示例不是完整公网部署方案。已有正常工作的 MediaMTX 配置无需替换。

也可在配置完成后使用 `./start.sh` 同时管理 MediaMTX 与应用。它需要 Linux、Bash 5.1+、`ss` 和 `setsid`；首次下载 MediaMTX 还需要 `curl`、`tar` 和网络。虚拟环境默认 `~/yolo_env`，可通过 `YOLO_VENV` 指定。脚本等待本次启动的 MediaMTX 监听 8554，默认超时 60 秒（可通过 `MEDIAMTX_START_TIMEOUT` 调整）；启动失败会退出，任一服务结束或按 Ctrl+C 会停止本次启动的另一服务。若已单独运行 MediaMTX，请直接启动 Python 应用。

## 配置

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| ENGINE_DIR | 应用所在目录 | 引擎目录 |
| PORT | 7860 | HTTP 端口 |
| MEDIA_WORKERS | 4（限制为1–4） | 服务端文件任务工作线程数 |
| ENGINE_CACHE_SIZE | 未设置时启动尝试保留全部模型 | 显式设置可限制模型缓存；显存不足时可能驱逐模型 |
| ENGINE_REPLICAS | 2（限制为1–4） | 每个常驻模型启动时尝试准备的实例数；设为1可关闭同模型多实例 |
| GPU_RESERVE_MB | 2048（最低512） | 加载实例时额外预留的显存，用于编解码和临时张量；不是显存占用硬上限 |
| MEDIAMTX_HTTP | http://127.0.0.1:8889 | WHIP/WHEP 信令地址 |
| MEDIAMTX_RTSP | rtsp://127.0.0.1:8554 | RTSP 地址 |

这些是进程环境变量；应用不会自动读取 .env。前端默认同时处理3项，资源紧张时先调为1项。

固定 640×640 模型在服务启动时完成预热；每个视频任务和 WebRTC 连接不再重复预热。被缓存逐出的模型重新使用时仍需加载初始化。WebRTC 编码器准备与 WHIP 信令并行，连接协商与首帧解码仍会产生启动延迟。JPEG 每个连接使用固定处理线程，优先使用 GPU JPEG 解码，失败时回退 CPU。

额外实例按设备实际空闲显存及模型内存估算决定是否加载。运行中空闲显存低于预留值，或推理发生显存不足时，会关闭额外实例并释放空闲副本；忙碌副本在当前推理结束后释放。显存不足推理最多重试一次；其他进程的显存占用变化仍可能导致任务失败。

## 性能与已知限制

- 历史测试：Tesla T10、1080p 样例、yolo26s_1920x1080.engine、预热30帧后测300帧，串行基准约39.51 FPS，平均25.308 ms/帧。这是独立基准结果，不代表当前并行版的完整回归结果。
- 部分实时配置曾反馈约60 FPS；不保证所有设备和分辨率达到60 FPS。
- 客户端画框显示本地新画面，检测框可能滞后；服务器画框对应同帧，但增加编码回传延迟。
- NVDEC 后仍存在 CPU BGR 转换/搬运，CPU 画框；不是全 GPU 零拷贝管线。
- FIFO 可向上游累积延迟；低延迟模式会丢弃待处理旧帧。
- 码率、帧率及分辨率优先均受浏览器实际支持限制。
- 无账号鉴权或用户隔离，任务状态保存在单进程内存中。请用于受信任网络，不要直接裸露到公网，也不要开启多个 Uvicorn worker。
- 停止是协作式取消，正在执行的 GPU 推理需等当前调用返回；音轨合成支持取消。任务源文件和结果从结束时刻起保留 15 分钟。
- 未完成最新版本 GPU 与浏览器端到端验证。

## 故障排查

启动找不到模型：检查 ENGINE_DIR、命名和输入尺寸。摄像头只有30 FPS：查看实际轨道与视频源统计，设备上限60并不表示该模式支持60。解码回退：提供终端中 [webrtc:...] 的异常类型和首帧日志，不应仅凭 invalid data 就认定硬件不支持。

## 首次使用：从模型到浏览器

1. **确认 GPU 环境**：在原有虚拟环境运行 nvidia-smi 查看驱动/GPU；确认 PyTorch 能使用 CUDA，并且 Ultralytics 与 TensorRT 能加载或导出你的模型。不要直接用 requirements.txt 替代 GPU 环境安装步骤。
2. **准备本地权重**：导出工具不自动下载权重。按实际型号将自备权重命名为 yolo26n/s/m/l/x.pt 并放在脚本目录，安装的 Ultralytics 版本须支持该模型。当前支持检测任务，不包含分割、姿态或分类任务。
3. **导出引擎**：先运行 --list 和 --check-env，再为选定型号导出 640×640 引擎，已有文件默认跳过。型号间输出文件互不覆盖。大模型需要更多显存、系统内存、磁盘空间和时间。
4. **启动服务**：模型不在脚本目录时设置 ENGINE_DIR，等待所有模型预热完成。预热失败的模型会从可选列表中移除；全部失败则终止启动，应根据预热日志排查。
5. **先试图片**：上传一张图片，确认模型、画框、预览和下载。
6. **再试视频**：用较短的视频确认输出时长、尺寸与音轨；先选择同时处理1项，再比较提高并发后的总完成时间。
7. **最后试实时**：先使用 HTTPS 页面验证 JPEG 摄像头路径，再启用 MediaMTX 与 WebRTC。

~~~bash
# 以自备的 yolo26m.pt 为例，文件已放在脚本目录
python export_all_engines.py --models m --list
python export_all_engines.py --check-env
python export_all_engines.py --models m
MEDIA_WORKERS=2 python app_ws-multi.py
~~~

## 三种场景怎么选

| 场景 | 建议起点 | 要注意什么 |
| --- | --- | --- |
| 单张或批量图片 | 文件上传 | 输出为服务器标注结果；高像素图片会增加内存与处理开销 |
| 需要完整保留的视频 | 文件上传 | 不按实时丢帧策略处理；处理FPS不等于成片播放FPS |
| 调试浏览器摄像头 | JPEG实时 | 每帧独立编码；JPEG质量影响带宽与编码开销 |
| 持续实时视频 | WebRTC | 有浏览器视频编码、网络协商、解码及播放缓冲 |
| 优先本地画面响应 | 客户端画框 | 本地视频较新，检测框来自稍早的服务器输入 |
| 要求框对应显示帧 | 服务器画框 | 帧与框一致，但额外经过编码、回传与播放 |

## 页面参数详解

### 图片与视频

- **模型**：选择现有 n/s/m/l/x 引擎，推理均为 640×640，素材宽高与模型输入独立。
- **自动选择策略**：速度策略优先 n，均衡优先 s，细节优先 x，缺少对应型号时从其余可用型号选择。手动指定引擎时按指定项执行。大模型不保证每种素材都更准确。
- **输出尺寸**：在原始画面上画框，图片保留原始尺寸；视频 YUV420 编码需要偶数宽高，奇数尺寸最多补一像素边缘。
- **置信度**：提高阈值会过滤更多低置信度结果；它不能保证消除所有重复框或误检。
- **同时处理**：前端可选1–4项，服务端还受 MEDIA_WORKERS 限制。默认前端3项、服务端最多4项。增加并发会增加CPU、内存、编解码和GPU竞争。
- **取消/重新开始**：每项可单独取消，不影响其他任务；完成、失败或取消后可按点击时页面选择的模型、策略和置信度重新开始；本次参数在入队时固定。保留期内复用服务器原文件，过期后由浏览器保留的 File 重新上传。处理期间可以追加任务。
- **删除/清除**：单项删除会取消该任务，并删除同一任务历次重启保留的文件；清空队列对全部记录执行同样操作。正在处理或下载的文件会在操作退出后清理。服务端最多接收 32 个未结束任务，工作线程数仍由 MEDIA_WORKERS 限制。

### 实时摄像头

- **比例和方向**：支持4:3与16:9及横竖屏展示；缩放时保留完整画面，可能出现补边。摄像头轨道报告的宽高与视频元素实际方向可能不同。
- **JPEG质量**：只影响JPEG管线。WebRTC使用视频编码，JPEG质量滑块不参与其中。
- **摄像头目标帧率**：10、15、20、24、25、30、40、45、50、60 FPS。默认 60，JPEG 和 WebRTC 共用此设置。是请求和发送上限，不能把 30 FPS 源变成真实 60 FPS。
- **WebRTC码率**：0.5、1、1.5、2、3、4、6、8、10、12、16、20、25、30、40、50 Mbps。上行是浏览器码率上限；服务器画框时同档位也用于回传编码目标，两者不是共享的一份带宽预算。
- **分辨率优先**：向浏览器请求 maintain-resolution；是否支持及实际调整由浏览器决定，页面显示读回情况。
- **FIFO**：最多4张应用待处理帧，按顺序处理；积压可能转移到上游缓冲，4帧不是端到端总缓冲上限。
- **低延迟**：应用只保留最新一张待处理帧，替换旧待处理帧；不取消正在执行的推理，也不能消除传输与播放缓冲。

改变WebRTC码率、帧率或队列模式会重新建立实时会话，短暂断开属于当前实现行为。

图片、视频和两条实时路径均可手动选择 YOLO26 n/s/m/l/x 引擎；实时列表默认优先 s 型号。摄像头可选 720p/1080p：16:9 为 1280×720/1920×1080，4:3 为 960×720/1440×1080，竖屏时交换宽高。硬件协商回退后的实际尺寸与帧率会显示在页面。使用 m/l/x 时可先将文件并发设为 1，并用 `ENGINE_CACHE_SIZE=1` 限制模型常驻数量。缓存限制不能解决单个模型本身超过可用显存的问题。

## 如何理解性能统计

**处理FPS与播放FPS不同。** 30 FPS视频可以以60帧/秒的速度离线处理，输出仍应按原时间戳播放；实时源只有30 FPS时，提高编码目标不会产生更多真实采集帧。

**不要把各阶段耗时相加后当作并行吞吐。** 流水线阶段能够重叠，队列等待也影响端到端延迟。多个视频时要同时记录每视频处理FPS和所有任务完成的总耗时。

**网络往返不等于视频延迟。** WebSocket ping、WebRTC候选对RTT、服务器处理时间和播放抖动缓冲测量的范围不同。界面中的传输/调度估计也不是纯网络传输时间。

建议比较时固定输入视频、引擎、置信度、画框方式、输出尺寸与并发数；区分首次加载和预热后的结果。提交性能问题时附上GPU型号、环境版本、配置、日志及持续运行时间。

## 基准测速

```bash
python benchmark_fps.py --list
python benchmark_fps.py --image /path/to/sample.jpg --variants s m --render server
python benchmark_fps.py --image /path/to/sample.jpg --source-sizes original --render none
```

默认对比四种源画幅：1280×720、1920×1080、960×720、1440×1080，所有型号的网络输入均为 640×640。`server` 模式包含原分辨率画框，`none` 模式只测预测与坐标后处理。计时不含图片读取、源画幅生成、视频编解码或网络，不代表实时视频端到端 FPS。未提供本地默认图片时使用合成画面，不联网下载；合成图的检测数量与画框开销不代表真实素材。显存峰值仅统计 PyTorch 分配器，不覆盖全部 TensorRT/CUDA 分配。

## 公网部署与数据处理

使用公网IP或DDNS时，webrtcAdditionalHosts 应填写客户端实际可达的IP或域名；仅设置DDNS或HTTPS不会自动完成UDP端口转发。示例中的自动网卡发现被关闭，不应只删 additional hosts 却不调整发现策略。

公网通常需要：可信HTTPS入口、支持WebSocket的反向代理、可达的UDP 8189，以及必要的路由/NAT配置。RTSP与内部信令端口继续仅绑定回环地址。普通HTTP代理不会自动代理WebRTC媒体。

当前没有用户鉴权与租户隔离。若公网开放，应在部署层统一保护网页、上传/下载API、WebSocket、WebRTC信令，并配置上传大小、连接数和访问限制。本项目未提供可直接替代这些保护的生产部署方案。

文件任务写入服务器临时目录，原文件和结果从任务完成、失败或取消时起保留 15 分钟；查看和下载不延长保留期。到期后拒绝新下载/复用请求，清理循环约每 10 秒执行一次；正在进行的下载结束后再删除。重新开始会建立新的任务与保留期限，单项删除可清理该任务历次重启文件。正常退出会清理临时文件；异常退出可能遗留，尚无跨重启清理机制。临时文件未做应用层加密，当前也没有用户隔离。

## 常见问题

| 现象 | 排查方向 |
| --- | --- |
| 未找到引擎 | ENGINE_DIR、文件名 yolo26s_640x640.engine、目录权限 |
| 引擎加载失败 | GPU/TensorRT兼容性、实际输入尺寸、显存；优先在目标机器重新导出 |
| 摄像头无法打开 | HTTPS信任、浏览器摄像头权限、设备占用、所选约束是否支持 |
| 选择60但实际30 FPS | 查看轨道、源、编码和发送FPS；设备能力上限不是当前组合保证 |
| WebRTC有页面但无视频 | MediaMTX运行状态、additional hosts、UDP8189、防火墙/NAT |
| NVDEC回退 invalid data | 查看首帧前后、异常类型与重试日志；可能涉及流启动或输入，不能仅凭错误认定GPU不支持 |
| 服务器画框明显更慢 | 比较编码/发布耗时和播放缓冲，再比较客户端画框 |
| 并发越高越慢 | 回到1项建立基准，再试2项；可用推理实例数、编解码和资源争用会限制收益 |
| 修改代码后页面没变 | 重启正确的服务进程并刷新页面，检查浏览器是否仍连接旧地址 |
